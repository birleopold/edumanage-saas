# Universal Time & Attendance Devices

EduManage's device-attendance layer is intentionally **vendor neutral**. The school owns one attendance model and one canonical event contract; vendor-specific hardware is translated at the boundary through a direct push adapter, vendor API puller, local edge connector, or CSV fallback.

## Why this architecture

A school attendance machine normally captures a user identifier, an event time and some device-specific context such as credential type, access event code or IN/OUT state. What varies is **how the machine exposes those facts**.

Current vendor documentation illustrates the variation:

- ZKTeco standalone systems commonly support Time Attendance PUSH / ADMS-style integration, and ZKTeco documents ADMS server configuration for devices as well as HTTP/HTTPS push connectivity. See: https://www.zkteco.com/en/ZKBio_WDMS and https://www.zkteco.com/en/faq/ADMS_configuration_on_Speedface_device
- ZKTeco also documents push-capable devices and credential combinations including face, fingerprint, palm, RFID, PIN and QR on supported product lines. See: https://www.zkteco.com/en/ZKBio_Time and https://www.zkteco.com/en/G4Pro
- Suprema BioStar 2 exposes local event-log search APIs, while Suprema G-SDK provides bulk and realtime event monitoring. Event objects include fields such as timestamp, deviceID, userID, eventCode and TNAKey. See: https://support.supremainc.com/en/support/solutions/articles/24000084862-biostar-2-api-how-to-get-event-logs-with-biostar-2-local-api and https://supremainc.github.io/g-sdk/api/event/
- Suprema's Time & Attendance API provides TNA log retrieval rather than requiring the school database to model Suprema-specific event objects. See: https://supremainc.github.io/g-sdk/api/tna/

Therefore, "works with any vendor" does **not** mean every physical machine can call the same endpoint without translation. It means a new vendor should normally require only a new adapter/edge connector, not a new Student table, a new HR model or a second attendance subsystem.

## Canonical event contract

New integrations should POST to:

```text
POST /api/v1/attendance/devices/events/
X-Device-Code: GATE-MAIN-01
X-Device-Key: <secret generated by EduManage>
Content-Type: application/json
```

Canonical event:

```json
{
  "event_id": "923448",
  "person_id": "STU-0042",
  "timestamp": "2026-08-10T07:42:18+03:00",
  "direction": "IN",
  "auth_method": "FACE",
  "event_code": "ACCESS_GRANTED"
}
```

Store-and-forward batch:

```json
{
  "source": "EDGE",
  "events": [
    {"event_id": "1001", "person_id": "27", "timestamp": "2026-08-10T07:30:01+03:00"},
    {"event_id": "1002", "person_id": "27", "timestamp": "2026-08-10T16:44:19+03:00"}
  ]
}
```

The batch maximum is 500 events. Exact event IDs are idempotent.

## Integration modes

### Direct push

Use when the device or vendor platform supports HTTPS push/webhooks. Configure the hardware/middleware to call the canonical API or place a vendor-specific translator in front of it.

### Vendor API pull

Use a vendor server/API to retrieve new event logs. Maintain the vendor cursor in `AttendanceSyncCursor`, translate each event, and POST to the canonical endpoint.

### Local edge connector

For SDK/LAN-only machines, deploy a small service on a school PC, mini-PC or Raspberry Pi. Its responsibilities are deliberately narrow:

1. connect to the local attendance device/vendor SDK;
2. read new event logs;
3. persist a local queue/cursor so internet loss does not lose punches;
4. translate logs into EduManage canonical events;
5. POST batches over HTTPS using the device code/key;
6. send heartbeat/device-time metadata;
7. retry safely using stable event IDs.

The edge connector should **not** calculate late/absent/payroll logic. School policy remains server-side in EduManage.

### CSV fallback

Use the admin import screen for machines with only USB/CSV export. Imported rows pass through the same vendor adapter, identity mapping, duplicate filtering and reconciliation pipeline as live events.

## Core domain objects

### AttendanceDevice

Represents a clock, biometric terminal, access controller, vendor server feed, or edge connector. It stores:

- stable device code and optional serial number;
- vendor/model/protocol;
- campus/location;
- push/pull/edge/file connection mode;
- identity namespace;
- timezone and clock offset;
- capabilities/settings;
- one-way hashed device secret;
- last-seen and last-event timestamps.

### AttendanceIdentity

Maps `(identity_namespace, external_person_id)` to exactly one student or staff member.

Namespaces prevent collisions. If Vendor A and Vendor B both use user number `1001` for different people, use different namespaces. If several clocks share one centrally provisioned user list, they may share a namespace.

### AttendanceEvent

Immutable raw evidence for a device punch. It preserves normalized fields and the original payload, including events that are duplicate, unmatched, ignored or erroneous.

The raw event ledger must not be rewritten when an administrator corrects attendance.

### AttendancePolicy

School-owned rules for interpreting punches:

- expected in/out time;
- late and early-departure grace;
- duplicate scan window;
- minimum presence minutes;
- weekdays;
- direction strategy;
- optional learner arrival/departure parent notifications.

Direction strategies:

- `DEVICE`: trust explicit IN/OUT from reliable hardware;
- `FIRST_LAST`: earliest punch is arrival, latest punch is departure; safest for simple gate machines;
- `ALTERNATE`: alternate accepted punches between IN and OUT.

### AttendanceDailyRecord

Reconciled student/staff daily presence with first-in, last-out, minutes present, lateness, early departure, source event count and manual-override flag.

### AttendanceAdjustment

Audit history for manual corrections. A correction changes the interpreted daily record, never the raw device punches.

## Gate presence versus class attendance

These are different facts and must remain different models.

A learner scanning at the gate proves campus presence. It does **not** prove the learner attended Mathematics at 10:00. Existing `AttendanceSession` / `AttendanceEntry` remain the source for lesson/class attendance.

The legacy biometric integration can still materialize a class attendance row when an explicit `offering_id` is supplied. Without an offering, the event only contributes to campus/staff presence.

## Security

- device secrets are generated by EduManage and stored only as SHA-256 hashes;
- plaintext secret is shown only immediately after creation/rotation;
- HTTPS should be mandatory in production;
- optional source IP allow-list can be configured per device;
- incoming batches are bounded;
- exact event replay is idempotent;
- identity mapping is explicit by default;
- auto-match uses exact active school IDs only when specifically enabled;
- raw vendor payloads remain tenant-scoped;
- the API handles attendance metadata, not biometric templates.

Fingerprint templates, face templates and similar biometric enrollment data should remain on the device/vendor platform unless a separate privacy/security-reviewed enrollment integration is intentionally added.

## Clock and offline behavior

A heartbeat can include device time:

```json
{
  "device_time": "2026-08-10T08:00:00+03:00",
  "capabilities": {"face": true, "rfid": true}
}
```

EduManage records approximate device clock offset. Original event time is retained during delayed uploads. Configurable protection can replace impossible future timestamps with server receipt time.

## Absence finalization

A device cannot prove absence until the school's expected arrival window has passed. Use either the admin daily-register action or schedule:

```bash
python manage.py finalize_device_attendance --previous-day --person-type ALL
```

Or scope it:

```bash
python manage.py finalize_device_attendance --date 2026-08-10 --campus MAIN --person-type STUDENT
```

The command respects active weekday policy and only creates missing ABSENT rows. It never overwrites an existing present/late/partial/manual record.

## Staff timekeeping and payroll

The device subsystem records trustworthy time evidence and provides a staff-timesheet CSV. Payroll should consume approved/validated attendance summaries only through an explicit payroll policy. Do not calculate salary deductions directly from raw punches because approved leave, duty travel, shifts, overtime, manual corrections and labor-policy rules are separate concerns.

## Legacy compatibility

`POST /api/v1/integrations/biometric/attendance/` remains available with its existing scoped integration API key. It now delegates to the universal event engine and preserves the legacy `BiometricAttendanceEvent` record for callers that depend on it.

New hardware integrations should use `/api/v1/attendance/devices/events/` instead.
