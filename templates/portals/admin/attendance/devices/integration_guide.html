Vendor-neutral architecture

One EduManage attendance model, several ways to reach it

No school-management API can force every physical clock to speak the same protocol. EduManage solves this by keeping one canonical event contract and translating vendor protocols at the edge or server boundary.

1. Direct push

Best when the device or vendor platform can POST events to HTTPS. Configure it to send to EduManage or use a small vendor-specific translator.

2. Vendor API pull

Use a vendor REST/gRPC/server API to fetch new logs using a cursor, normalize them, then POST the canonical events to EduManage.

3. Local edge connector

For LAN-only SDKs, run a lightweight service on a school PC/Raspberry Pi. It talks to the machine locally and securely forwards normalized events.

4. CSV fallback

For very old equipment, export logs and import them. EduManage still applies identity mapping, duplicate filtering and policy reconciliation.

Canonical event contract

Adapters may accept many vendor field names, but this is the clean payload your own middleware should produce.

POST /api/v1/attendance/devices/events/
X-Device-Code: GATE-MAIN-01
X-Device-Key: <one-time generated secret>
Content-Type: application/json

{
  "event_id": "923448",
  "person_id": "STU-0042",
  "timestamp": "2026-08-10T07:42:18+03:00",
  "direction": "IN",
  "auth_method": "FACE",
  "event_code": "ACCESS_GRANTED"
}

Batch / store-and-forward contract

Edge connectors can queue events while offline and upload them later without losing the original punch time.

{
  "source": "EDGE",
  "events": [
    {"event_id":"1001","person_id":"27","timestamp":"2026-08-10T07:30:01+03:00"},
    {"event_id":"1002","person_id":"27","timestamp":"2026-08-10T16:44:19+03:00"}
  ]
}

Maximum batch: 500 events. Exact event IDs are idempotent; resending the same event does not create another attendance punch.

What “vendor independent” really means

EduManage owns the attendance semantics and database. A new vendor normally requires an adapter or edge connector only—not a new Student table, a new payroll model, or a new attendance workflow.

Heartbeat and clock control

A connector can POST device_time and capabilities to /api/v1/attendance/devices/heartbeat/. EduManage records estimated clock offset so administrators can detect a machine that is drifting.

Identity lifecycle

The machine's user number is mapped through an identity namespace. A person can therefore move campuses, replace a card, or be enrolled on a new device without changing their EduManage student/staff primary key.

Biometric privacy boundary

This interface receives attendance event metadata—not fingerprint templates or face images. Biometric templates should remain on the device/vendor platform unless a separately reviewed enrollment integration is intentionally built.

Class attendance remains separate

A gate punch proves campus presence, not lesson participation. If a vendor/middleware supplies a specific offering_id, the legacy compatibility endpoint may create a class-attendance entry; otherwise it only updates campus/staff presence.
